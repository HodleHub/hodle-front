## Resumo executivo

Não encontrei bloqueio técnico de indexação no site público durante esta revisão. O verificador executado contra `https://hodle.com.br` passou em 50 URLs do sitemap, 37 assets JS/CSS e 8 imagens sociais. As páginas verificadas retornaram HTTP 200, canonical próprio, um H1, idioma esperado, sem `noindex` e com JSON-LD sintaticamente válido; as rotas desconhecidas testadas retornaram 404.

Os arquivos públicos `llms.txt`, `llms-full.txt` e `llm.txt` têm o mesmo SHA-256 que os arquivos do commit revisado. Quatro amostras de Markdown — LLC em inglês, CaaS, artigo PSAV e glossário — responderam `text/markdown`. Isso confirma que o deploy observado estava sincronizado com a base quanto a esses arquivos e que os contratos de rastreabilidade principais estavam ativos.

Os achados preliminares da execução interrompida sobre localização, compartilhamento e links contextuais já foram cobertos pelos PRs #94–#96. Não os repliquei. O ponto P1 restante é a falta de uma rotina recorrente: o verificador existe, mas não há workflow agendado e o deploy é manual. Não há incidente atual de deploy identificado.

Não havia credenciais ou dados do Google Search Console disponíveis nesta execução. Portanto, este documento não afirma volume de busca, posição, CTR, tráfego, canibalização ou impacto de ranking.

## Achados priorizados

### P0 — nenhum

Nenhuma falha observada impede rastreamento ou indexação das páginas públicas listadas no sitemap.

### P1 — falta uma auditoria recorrente após as mudanças

**Evidência.** `scripts/verify-public-seo.mjs` já percorre o sitemap e valida status, canonical, H1, idioma, indexação, JSON-LD, imagens sociais, navegação, Markdown, sandbox e 404. Não há diretório `.github/workflows` neste commit. `deploy.md` informa que o deploy para Vercel é manual e que merge em `main` não publica automaticamente.

**Correção proposta.** Agendar semanalmente o verificador existente em um workflow com execução manual e guardar relatório datado como artifact. Incluir deltas de URLs, metadados e falhas. A execução deve fazer somente GET ao site público; não deve publicar, chamar IndexNow ou usar API paga. Search Console só entra com acesso de leitura já existente e autorizado.

**Impacto esperado.** Reduzir o tempo para detectar uma regressão de canonical, sitemap, 404, schema, idioma, Markdown ou imagem social de uma revisão eventual para até uma semana. O relatório atual não identificou quebra em produção.

**Issue proposta.** `[SEO] Automatizar auditoria semanal e revisão com dados first-party`. O texto da issue foi preparado nesta retomada, mas a criação no GitHub foi rejeitada pelo MCP; não há URL de issue para vincular.

### P2 — revisar seis snippets longos com evidência de SERP

**Evidência.** A extração do HTML publicado encontrou descriptions com mais de 160 caracteres em `/faq` (165), `/legal` (169), `/neobank` (173), `/crypto-as-a-service` (167), `/articles/comparar-api-pix-baas` (166) e `/articles/auto-custodia-nao-e-detalhe-de-implementacao` (166). Exemplos de origem: `src/app/(pt)/faq/page.tsx:8-11`, `src/app/(pt)/neobank/page.tsx:52-55`, `src/app/(pt)/crypto-as-a-service/page.tsx:34-36` e os frontmatters dos dois artigos.

**Correção proposta.** Conferir esses seis URLs em consultas reais no Search Console antes de editar; encurtar somente quando a description não resume bem a página ou o snippet exibido perde a informação principal. Não aplicar um corte automático em 160 caracteres: o Google não define limite fixo e pode gerar snippets diferentes conforme a consulta e a largura do dispositivo.

**Impacto esperado.** Melhorar a clareza do texto exibido e potencialmente o CTR em consultas comerciais. Não há impacto de ranking garantido nem evidência de queda atual.

### P2 — completar o idioma Open Graph em dez páginas informativas

**Evidência.** No HTML público, `og:locale` está ausente em `/faq`, `/legal`, `/privacidade`, `/termos`, `/cookies`, `/ai`, `/glossario`, `/contato`, `/desenvolvedores` e `/articles`. A metadata global define `pt_BR` em `src/app/siteDocument.tsx:56-72`, mas esses segmentos substituem o objeto `openGraph` e não repetem `locale`; por exemplo, `src/app/(pt)/faq/page.tsx:15-21`, `src/app/(pt)/legal/page.tsx:13-19`, `src/app/(pt)/articles/layout.tsx:12-18` e `src/utils/infoPageMetadata.ts:22-27`.

**Correção proposta.** Definir `locale: 'pt_BR'` no helper de páginas informativas e nos overrides restantes. Manter `en_US` nas páginas inglesas, que já o informam.

**Impacto esperado.** Tornar explícito o idioma para consumidores Open Graph e plataformas de compartilhamento. O campo não é um bloqueio de indexação nem um fator de ranking conhecido.

### P2 — medir Core Web Vitals antes de aumentar a hidratação

**Evidência.** O PR #97 reduziu o HTML comprimido em 8–11% em `/`, `/neobank` e `/crypto-as-a-service`, enquanto aumentou o JavaScript inicial em 3–5 kB nessas páginas. O próprio PR registra que não foi exercitado em navegador real. As páginas continuam abaixo do orçamento interno de 1,5 MB por arquivo; esse orçamento é de crawl, não uma medição de experiência.

**Correção proposta.** Obter uma linha de base de CrUX/PageSpeed ou RUM autorizado para LCP, INP e CLS nos três templates antes de novos componentes cliente motivados só pelo tamanho bruto do HTML. Preservar o conteúdo no HTML inicial.

**Impacto esperado.** Priorizar mudanças com base em experiência medida em dispositivos reais e evitar trocar bytes de HTML por custo de hidratação sem benefício demonstrado.

### P2 — calibrar a expectativa sobre FAQPage no Google

**Evidência.** O site mantém FAQs visíveis e JSON-LD coerente; a auditoria confirmou que os blocos JSON-LD publicados são parseáveis. A documentação do Google informa que FAQ rich results são exibidos apenas para sites governamentais e de saúde conhecidos e autoritativos. A Hodle não pertence a essas categorias.

**Correção proposta.** Manter a marcação quando representar conteúdo visível e útil a outros consumidores, mas não prometer ganho de CTR ou rich result do Google por causa de `FAQPage`. Validar semântica de schema separadamente do parse JSON.

**Impacto esperado.** Planejamento de SEO mais realista. Não recomendo remover a marcação só por essa limitação; o Google diz que dados estruturados não utilizados não prejudicam a Pesquisa.

## Aprendizados do open-seo

Fontes consultadas: [repositório](https://github.com/every-app/open-seo), [README](https://github.com/every-app/open-seo/blob/main/README.md), [documentação MCP](https://github.com/every-app/open-seo/blob/main/web/content/docs/mcp.md), [licença](https://github.com/every-app/open-seo/blob/main/LICENSE) e [Search Console self-hosted](https://github.com/every-app/open-seo/blob/main/docs/SELF_HOSTING_GOOGLE_SEARCH_CONSOLE.md).

- **O que faz e arquitetura:** aplicação de SEO com interface web, MCP e Agent Skills. A documentação descreve integração com pesquisa de palavras-chave, SERP, rastreamento de posições, concorrentes, backlinks, auditorias, visibilidade de IA e consultas/inspeção do Search Console. O projeto usa stack web e persistência própria; opções publicadas de self-host são Docker para uso pessoal e Cloudflare para uso compartilhado.
- **Workflows:** pesquisa de palavras-chave, inspeção de SERP, auditoria, posição, concorrentes/backlinks e visibilidade de IA são fluxos explícitos. Não encontrei um fluxo dedicado de content briefs na documentação consultada; para Hodle, briefs ainda precisam registrar consulta-alvo, intenção, evidência, URL canônica, perguntas, links internos e data de revisão.
- **Licença e custo:** o repositório informa licença MIT. Dados de SEO via DataForSEO exigem chave própria e são cobrados por uso; Search Console é uma fonte opcional que precisa de autorização Google configurada. Não recomendo adotar ou self-hostar o produto inteiro sem primeiro decidir orçamento, fonte de dados e responsável.
- **O que reaproveitar:** portar o desenho de workflows reutilizáveis e relatórios com contexto salvo para o verificador, o registry de tópicos e o measurement plan existentes. Começar por uma rotina técnica gratuita/read-only e só incluir dados pagos de SERP/backlinks mediante decisão explícita. O artifact do GitHub Actions pode ser a primeira entrega; Discord requer integração separada.
